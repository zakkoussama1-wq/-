# تجهيز نشر نموذج Shopify — المرحلة الثانية

هذا الدليل يفصل نشر خادم Next.js على Render عن إصدار Theme App Extension في
Shopify. رفع GitHub أو بناء Docker لا يضيف البلوك إلى الثيم. جميع أوامر الربط
والنشر أدناه ينفذها مالك التطبيق لاحقًا؛ لم ننفذها على التطبيق الحقيقي.

## حالة التحقق وحدوده

- لا يوجد في المستودع `shopify.app.toml` حقيقي أو Client ID موثق؛ يوجد قالب فقط.
  لذلك **هوية التطبيق والربط الحقيقي غير مؤكدين**. اسم DZ Lead Form Pro وحده لا
  يثبت الهوية، وملف `shopify.extension.toml` لا يحدد التطبيق الأب.
- يجب أن يتطابق Client ID بين تطبيق DZ Lead Form Pro في Dev Dashboard، وإعداد
  `SHOPIFY_CLIENT_ID` الموجود على Render، والملف المحلي الذي يسحبه CLI. المقارنة
  لا تحتاج عرض Client Secret أو Access Token. لا تغيّر معرف Render ليلائم تطبيقًا آخر.
- استخدمنا حزمة Shopify CLI الرسمية المثبتة بالإصدار `5.0.1` من سجل npm الرسمي،
  وراجعنا مساعدة `app config link` و`app build` و`app deploy` و`app release` و`theme check`.
  يتطلب هذا الإصدار Node >=22.12؛ المشروع نفسه يتطلب Node 24 وnpm >=11 وGit.
- نجح Theme Check الرسمي بهدف `theme-app-extension` دون أخطاء أو تحذيرات.
  اكتشف الفحص الأول تجاوز ملف schema JavaScript حد 10,000 بايت؛ أصبح ملف التهيئة
  نحو 1.4 كيلوبايت، ويحمل runtime عند اقتراب البلوك من الشاشة. لم نرفع حدود الفحص أو نعطله.
  runtime حجمه نحو 707 كيلوبايت خامًا؛ يبقى قياس أدائه على اتصال هاتف حقيقي مطلوبًا.
- shopify.dev محجوب بسياسة شبكة هذه البيئة. تحققنا من الأوامر والمخططات التي
  تتضمنها أداة Shopify الرسمية، لكن التحقق من الحساب الحقيقي ورفع الامتداد
  والمخطط الحي لـ2026-10 يحتاج بيئة المالك. لا نعتبر بيانات الاختبار إثباتًا لربط حقيقي.

## 1. نشر الخادم والتحقق من السلامة

انشر Commit المعتمد على Render بالطريقة الحالية، مع إبقاء
`DZ_SHOPIFY_ORDER_SYNC=0` وجميع حواجز التجربة كما هي. لا تحتاج هذه المرحلة ترحيلًا
أو حذف بيانات. لم تتغير صفحات الطلبات القديمة أو OAuth أو عامل المزامنة.

تأكد من صحة `/api/health` ومن أن Bootstrap Mode غير مفعل في الخدمة العاملة.
فتح `/api/storefront/bootstrap` مباشرة دون توقيع ينبغي أن يفشل؛ هذا متوقع ولا
يعني أن المصادقة تحتاج تعطيلًا. يعتمد النموذج على Offline Token صالح لهوية التطبيق
نفسها و`read_products`، ومفتاح التشفير الحالي وأسعار الشحن الحقيقية؛ لا تغيّر المفاتيح.

## 2. ربط نسخة محلية بالتطبيق الصحيح

نفذ من جذر المشروع على جهاز موثوق، بحساب Shopify الذي يملك التطبيق. لا تستخدم
`app init` ولا تنشئ تطبيقًا جديدًا. لا تنسخ القالب فوق إعدادات التطبيق الحالية.

```sh
npm ci
npm run storefront:build
npx --yes @shopify/cli@5.0.1 app config link --client-id YOUR_VERIFIED_CLIENT_ID
```

يسحب `app config link` إعدادات التطبيق إلى ملف محلي؛ لا ينشر إصدارًا. راجع الهوية
والمنظمة و`client_id`، وأوقف العملية إذا اختلفت. الملفات الحقيقية
`shopify.app.toml` و`shopify.app.*.toml` و`.shopify/` مستثناة من Git وDocker.
احتفظ بمعرف الامتداد/UID الذي يديره CLI بعد الربط أو النشر الأول، ولا تولّد امتدادًا
بديلًا في كل نشر. لا تنسخ UID من تطبيق مختلف.

احتفظ بـapplication_url وredirect_urls وembedded والتوزيع وwebhooks والصلاحيات
والامتدادات الحالية كما هي في الملف المسحوب. أبقِ
`automatically_update_urls_on_dev=false`. لا تشغل `app dev` على الإنتاج؛ قد يغير
عناوين التطبيق إلى نفق تطوير. لا تستخدم `--verbose` مع بيانات الإنتاج.

## 3. App Proxy والصلاحيات

أضف أو راجع القسم التالي في **الملف المسحوب للتطبيق الصحيح**، مستخدمًا نفس مضيف
HTTPS الحقيقي للخدمة، دون `/dashboard` أو شرطة نهائية في URL:

```toml
[app_proxy]
url = "https://YOUR_RENDER_HOST/api/storefront"
prefix = "apps"
subpath = "dz-cod"
```

يصل `/apps/dz-cod/bootstrap` إلى `/api/storefront/bootstrap`، وبالمثل
`communes` و`quote` و`validate`. يوقع Shopify الطلبات ويُتحقق منها بالـClient Secret
الحالي. لا تُضاف أسرار أو توكنات إلى الثيم، ولا يلزم Storefront API Token.

راجع متطلب `write_app_proxy` في إعداد التطبيق وصلاحيات الإصدار قبل الحفظ؛ لا تفترض
أن `write_orders` يمنحه. أبقِ `read_products` والصلاحيات الحالية، ولا تضف
`write_themes` أو صلاحيات العملاء أو المخزون أو `read_orders` من أجل هذا النموذج.
إذا طلب Shopify موافقة جديدة بسبب الصلاحية، ينفذها المالك دون حذف التطبيق.
مسار OAuth الحالي لم يتغير ويطلب نطاقاته الحالية فقط؛ زر إعادة الربط الحالي ليس
دليلًا على منح `write_app_proxy`. أكّد متطلبات المنح في Dev Dashboard عند نشر الإصدار،
وأوقف النشر إن اشترطت تغيير تدفق التفويض حتى يُراجع هذا التغيير منفصلًا.

لكل تطبيق App Proxy واحد: إن كان هناك Proxy موجود يستخدمه جزء آخر، فإن استبداله
قد يكسر ذلك الجزء. راجع قيمته واستخداماته قبل تغييره. كذلك يمكن تخصيص مسار Proxy
على مستوى المتجر؛ إذا كان مختلفًا، اجعل إعداد البلوك يطابق المسار الفعلي، ولا تفترض
أن نشر الإصدار يعيد ضبط تخصيص المتجر تلقائيًا.

## 4. فحص الامتداد وإصدار Shopify جديد

بعد مطابقة الهوية ومراجعة الفرق في إعدادات التطبيق:

```sh
npm run storefront:build
npx --yes @shopify/cli@5.0.1 theme check --path extensions/dz-cod-form --no-input
npx --yes @shopify/cli@5.0.1 app build
npx --yes @shopify/cli@5.0.1 app deploy --no-release --version dz-cod-phase2-preview
```

الأمر الأخير **يرفع إصدارًا حقيقيًا إلى Shopify** لكنه لا يصدره للتجار. لا تنفذه
قبل مطابقة الهوية. راجع في Dev Dashboard أن الإصدار يحتوي البلوك الجديد وApp Proxy
المقصود، وأنه لا يحذف امتدادًا أو webhook ولا يغير عناوين OAuth والصلاحيات الحالية
عن غير قصد. `app deploy` يلتقط إعدادات التطبيق والامتدادات معًا، وليس هذا البلوك وحده.
لا تستخدم `--allow-deletes` أو `--allow-updates` لتجاوز المراجعة، ولا تتجاوز الفحص
بـ`--no-build`. لا تستخدم `--client-id` على deploy لتحويل الإعداد إلى تطبيق آخر.

عندما تقرر إتاحة الإصدار بعد مراجعته:

```sh
npx --yes @shopify/cli@5.0.1 app release --version dz-cod-phase2-preview
```

الإصدار الجديد مطلوب لإتاحة Theme Extension وتعديل Proxy للمستخدمين. الإصدار
ليس مجرد نشر Render؛ قد يطبق تغييرات إعدادات التطبيق على التثبيتات الحالية. أبقِ
باقي التكوينات الحالية محفوظة. لا حاجة لإزالة التطبيق أو إعادة تثبيته لحذف البيانات.
قبل تغيير النسخة الحية، سجل الإصدار السابق لتتمكن من إعادة إصداره إذا لزم.

## 5. إظهار النموذج واختبار الواجهة فقط

1. افتح Online Store → Themes → Customize، ويفضل أولًا على نسخة من الثيم الحالي.
2. افتح قالب المنتج وأضف Apps → DZ COD Form في قسم يدعم App Blocks، أو قسم Apps
   أسفل تفاصيل المنتج. مكان العرض بجانب الصور يعتمد على نقاط الإضافة التي يوفرها الثيم.
3. اضبط App Proxy path على `/apps/dz-cod` أو المسار الفعلي المخصص، واللغة والألوان
   والنصوص. احفظ نسخة الثيم، ثم افتح معاينة المنتج الفعلي من المتجر؛ لا تستخدم
   رابط Render لاختبار App Proxy. إن لم يظهر البلوك، تحقق أولًا من إصدار التطبيق
   ومن دعم القالب لـApp Blocks وصلاحية المتجر والتطبيق، لا من إعدادات المزامنة.
4. اختبر العربية والفرنسية والإنجليزية، العرض على الهاتف، المتغير والكمية وصورة
   المنتج، وولاية/بلدية لها أسعار معروفة. يجب أن يتطابق الإجمالي مع الأسعار المحفوظة،
   وأن تبقى الطرق المعطلة غير متاحة. اختبر تغير المتغير في عناصر الثيم أيضًا.
5. جرب التوصيل للمنزل والعنوان المطلوب، والمكتب العام عند السماح به فقط. لا توجد
   قائمة مكاتب فعلية في هذه المرحلة ولا تُختلق عناوين أو معرفات مكتب.
6. تأكد من ظهور إشعار المعاينة. زر النموذج يتحقق فقط ويعيد
   `validated=true, persisted=false, shopifyOrderCreated=false`. لا ينشئ طلبًا حتى
   إذا غُيّر نص الزر. اختبر ببيانات صناعية؛ لا تستخدم بيانات عملاء في لقطات الشاشة.
7. حدّث قسم المنتج وغيّر المتغير، وتأكد من بقاء نموذج واحد. تحقق من عدم وجود
   طلبات Shopify أو سجلات طلب محلية جديدة أو إشعارات أو Purchase أو تغير مخزون.

المتوقع: النموذج يظهر ويحسب الأسعار عبر Proxy الحقيقي، بينما استقبال الطلبات
والمزامنة يظلان معطلين. المنتج يجب أن يكون ACTIVE ومنشورًا للمتجر الإلكتروني،
والعملة DZD. النطاقات المقبولة هي primary domain وmyshopify؛ نطاق Markets إضافي
يحتاج مراجعة. صور Jeep Buluo المرجعية لم تصل بعد؛ المطابقة البصرية الدقيقة مؤجلة.

## نتائج المراجعة المحلية

- 308 اختبارات Vitest ناجحة، منها اختبارات PostgreSQL 18 في قاعدة محلية معزولة
  وShopify وهمي؛ لا يستخدم أي اختبار متجرًا حقيقيًا.
- 20 اختبار متصفح ناجحة على الهاتف وسطح المكتب، تشمل التحميل المؤجل وفشل تنزيل
  runtime وإعادة المحاولة ورفض مصدر غير موثوق ومنع تكرار النموذج وتحديث الأسعار.
- Lint وفحص الأنواع والتنسيق ناجحة، وفحص الملفات الجديدة/المعدلة لم يجد أنماط
  اعتمادات حقيقية. بيانات الاعتمادات داخل الاختبارات صناعية.
- Theme Check الرسمي: `valid=true` و0 أخطاء و0 تحذيرات؛ `app build` الرسمي نجح
  باستخدام نسخة مؤقتة من قالب الإعدادات، مع تخطي تثبيت الاعتماديات. هذه نتيجة
  للبناء المحلي فقط، وليست تأكيدًا لـClient ID أو ترخيص أو نشر حقيقي.
- بناء Docker ناجح؛ لا يحتوي هذا التغيير على ترحيل PostgreSQL جديد أو تعديل
  ملفات المزامنة أو OAuth أو الطلبات القديمة. لا نشغل الخادم/العامل من صورة
  الاختبار على بيانات الإنتاج.
