# تجربة متجر h8vsym-t0.myshopify.com — الاتصال والمنتجات

الهدف الحالي هو متجر المالك فقط؛ لا تُضاف فوترة أو اشتراكات أو توزيع عام. حُفظت ضمانات عزل الحسابات السابقة. لم يُثبت التطبيق في Shopify ولم تُنشأ استضافة أو تُعدّل ثيمات أو تُرسل طلبات أو أحداث إعلانات.

## الاتصال الفعلي: ما يزال ينتظر المالك

فحص البيئة الحالية أكد غياب DATABASE_URL وSHOPIFY_CLIENT_ID وSHOPIFY_CLIENT_SECRET وSHOPIFY_REDIRECT_URI وINTEGRATIONS_ENCRYPTION_KEY. لا يوجد HTTPS عام مُعد للتطبيق. البيئة تعمل والاختبارات المحلية لا تثبت ملكية المتجر أو صحة اعتماده. لا تطلب إدخال الأسرار في المحادثة.

1. افتح Shopify Admin → Settings → Apps → Develop apps → Dev Dashboard، أو https://dev.shopify.com/dashboard.
2. افتح تطبيق التجربة السابق أو Apps → Create app. لا تنشئ مشروع مصدر بديل. إن لم تختر Distribution بعد، راجع أن Custom distribution مناسب لمتجر المالك لكنه قد يتطلب تطبيق Public منفصلًا لاحقًا. لا تختَر App Store في هذه المهمة.
3. وفّر عنوان HTTPS لخادم Next.js وPostgreSQL للتجربة، دون إنشاء خدمة مدفوعة تلقائيًا. دومين المتجر لا يستضيف خادم التطبيق. يمكن استعمال استضافة تملكها أو tunnel مؤقت مصرح به؛ لم يُفتح tunnel في هذه الجلسة. لا تستخدم app dev على متجر مدفوع عادي؛ معاينات CLI تتطلب متجر تطوير أو Plus sandbox مؤهلًا.
4. في مسودة App version اضبط App URL على `https://APP_HOST/dashboard`، وألغِ Embed app in Shopify admin، وAllowed redirect URL على `https://APP_HOST/api/integrations/shopify/callback`، والنطاق read_products فقط، وAPI version 2026-10. أبقِ authorization-code flow الموافق للقالب الحالي. خطوة Release/اختيار التوزيع والتثبيت تتم بمراجعة المالك داخل حسابه؛ لا يُساوى تفعيل إصدار اختبار خاص بنشر App Store.
5. أدخل القيم الآمنة في الخادم مباشرة، لا في Git أو المحادثة. SHOPIFY_SHOP هو `h8vsym-t0.myshopify.com`. الأسرار المستخدمة لـHMAC وAES يجب أن تكون متاحة للعملية محليًا، لا placeholders تستبدل فقط عبر proxy. لا تستبدل مفتاح التشفير الموجود.
6. شغّل `node scripts/production-preflight.mjs` ثم `npm run build` و`npm start` من جذر المستودع مع المتغيرات المحقونة. standalone يحتاج preflight قبل server.js أيضًا. لم يُختبر نشر حي. لا تغيّر إعدادات DNS/ثيم متجر فعلي لتجربة الخادم.
7. افتح التطبيق عبر HTTPS، وسجّل الدخول بحساب التاجر نفسه، ثم التكاملات → بدء ربط المتجر → متابعة التفويض على Shopify. راجع صلاحية read_products والموافقة الرسمية. بعد العودة اضغط **التحقق الحي من الاتصال**؛ نجاحه يتطلب طلب Admin API حقيقيًا، لا مجرد وجود رمز مخزن.
8. اضغط **مزامنة منتجات Shopify** ثم افتح المنتجات. الزر يسجل اشتراكات المنتجات المطلوبة للاتصالات القديمة أيضًا. إذا فشل التسجيل لا يُعرض نجاح مزامنة وهمي. لا تحتاج كتابة منتجات يدويًا.

إعداد شبكة البيئة المحفوظ في المسودة يحتاج مراجعة/حفظ وتفعيل نسخة البيئة؛ الحفظ السابق ليس دليلًا على تطبيقه. جهات Shopify المطلوبة محفوظة مسبقًا. لا تعرض بيانات الاعتماد أو اتصال قاعدة البيانات في سجلات الفحص.

## ما أُنجز في مرحلة المنتجات

- جلب Admin GraphQL باستخدام رمز التاجر المخزن والمجدد بأمان، مع مقارنة Shop GID بالهوية المثبتة.
- pagination للمنتجات والخيارات بصورة مستقلة. تُرفض المؤشرات المكررة والمنتجات أو الخيارات المكررة والاستجابات غير الصالحة بدل نشر لقطة ناقصة. حد الأمان 100 ألف منتج و2048 خيارًا للمنتج.
- الحقول: Product/Variant GID، العنوان والوصف النصي، صور المنتج (أول 12 للمعرض الحالي)، صورة الخيار، SKU، selectedOptions التي تتضمن اللون/المقاس حسب تعريف التاجر، السعر وبيانات المخزون وسياسة الاستمرار بالبيع.
- الأسعار تُحوّل بدقة إلى centimes من السلسلة دون تقريب float. التطبيق الجزائري الحالي يقبل عملة DZD فقط؛ تُرفض العملات الأخرى صراحة، ولا نحول سعرًا أجنبيًا إلى دينار افتراضيًا. لا تغير عملة متجرك تلقائيًا.
- الكمية من inventoryQuantity وسياسة inventoryPolicy ليست ضمانًا لتوفر قناة بيع أو مخزون محجوز. التحقق الحي الملزم بالكمية والتسعير عند إنشاء طلب Shopify في مرحلة الطلبات لاحقًا.
- كتالوج Shopify مستقل في auth/PostgreSQL عن checkout_products المحلي والطلبات السابقة. لا تُحذف منتجات محلية أو سجلات طلبات لإخفاء demo.
- حفظ اللقطة كاملًا في معاملة واحدة. عند خطأ API/عملة/صفحة، تبقى اللقطة السابقة ولا تُستبدل ببيانات جزئية؛ الطلب يفشل وتُحفظ حالة sync_failed العامة دون رمز أو استجابة مزود حساسة.
- أول قراءة للكتالوج بعد OAuth تجلب المنتجات تلقائيًا. اللقطة صالحة لدقيقة؛ القراءة التالية أو المزامنة اليدوية تعيد مطابقة الكتالوج كاملًا، فتزيل المنتجات المحذوفة من لقطة Shopify فقط. هذه reconciliation عند القراءة، وليست ادعاء تشغيل worker دائم أو push فوري دون طلب.
- واجهة المنتجات في وضع Shopify تقرأ وتعرض المنتجات وتخفي الإنشاء والتحرير والنسخ المحلي وروابط النموذج غير الجاهز. يظهر رابط تعديل حقيقي في Shopify. تُعاد القراءة عند التركيز وعلى فاصل دقيقة عندما تكون الصفحة ظاهرة.
- الترجمة العربية/الفرنسية/الإنجليزية محفوظة. عند فشل التحميل تظهر رسالة خطأ مع إعادة محاولة، ولا تُنشأ منتجات وهمية.
- في الإنتاج، تعطيل تكامل Shopify يسبب فشلًا واضحًا ولا يرجع إلى منتجات محلية. التطوير الافتراضي يبقى demo منفصلًا؛ `DZ_SHOPIFY_MODE=1` يسمح بتجربة كتالوج Shopify في بيئة تطوير مصرح بها، مع تعطيل DZ_LOCAL_DEMO واستخدام قواعد منفصلة.

## Webhooks

يُسجل OAuth اشتراكات APP_UNINSTALLED وPRODUCTS_CREATE وPRODUCTS_UPDATE وPRODUCTS_DELETE خاصة بالمتجر، عبر GraphQL. لا تُخلط باشتراكات TOML غير المتوافقة مع legacy install flow. المسار `/api/shopify/webhooks` يتحقق من HMAC قبل JSON والحجم ومعرّف التسليم. أحداث المنتج تُعلّم كتالوج المتجر المرتبط بأنه يحتاج مزامنة؛ لا يثق الكود بأسعار body ولا يكتب منه كتالوجًا أو طلبات. التسليم المكرر لا يُعيد تغيير الحالة بعد معالجة الحدث، والمتجر غير المرتبط لا يعدل كتالوج متجر آخر. التسجيل الفعلي ووصول Shopify إلى HTTPS لم يُختبرا بعد.

## المخطط والفحوص

الترحيل الإضافي `scripts/migrations/003_shopify_catalog.sql` ينشئ shopify_catalog وshopify_catalog_dirty، ويتضمنهما المخطط الكامل وسكربت نقل SQLite إلى PostgreSQL. اختُبر تطبيقه مرتين داخل schema محلي مؤقت مع بقاء اللقطة. الرجوع للكود السابق يتم مع الخدمة متوقفة وبإبقاء الجداول والبيانات؛ لا DROP ولا إعادة توليد مفتاح.

نقطة الرجوع: `6ad54699a9e70c9c0eb5314458d9189301e78edc`، والوسم `checkpoint/pre-store-products-6ad5469`. النسخ: `/workspace/dz-backups/pre-store-products-default` و`pre-store-products-demo` مع manifests وفحص سلامة SQLite.

اختبارات المزامنة تستخدم محاكاة HTTP فقط، وتُشغّل أيضًا على PostgreSQL محلي للتحقق من المعاملات والترحيل؛ ليست اختبارات اتصال متجر حي. اختبارات الواجهة تتحقق من القراءة فقط وأزرار المزامنة والتعافي باللغات الثلاث بمحاكاة النقل. لا توجد نتيجة قبول نهائي للنظام من مجرد نجاح هذه الاختبارات.

## ما لم يُنفذ بعد

Theme App Extension وApp Block وسياق واجهة المتجر الموقّع وربط نموذج العميل بالشحن هي المرحلتان 3 و4. إنشاء طلب Shopify المتوافق والتثبت من سياسة Checkout وآثاره مرحلة 5؛ الطلب المحلي لا يُقدّم بوصفه طلب Shopify. المزودون الحقيقيون وإعدادات الإعلانات مرحلة 6، وPurchase الإنتاجي غير مصرح. لا توجد عملية مدفوعة أو تعديل للثيم الحي في هذه المرحلة.

## نتيجة هذه الجلسة

نجحت فحوص lint والأنواع والبناء، و194 اختبارًا عامًا مع تخطي 6 حالات PostgreSQL اختيارية في المجموعة العامة. شُغّلت حالات PostgreSQL ضمن مجموعة مستقلة: 18 حالة ناجحة، متداخلة مع المجموعة العامة وليست أعدادًا تُجمع. نجحت 26 حالة متصفح سابقة و6 حالات جديدة لواجهة Shopify (محاكاة HTTP) بكل اللغات وعلى الهاتف والحاسوب. أُصلح أيضًا عائق bootstrap: يستطيع الحساب الجديد قراءة حالة الاتصال وبدء التفويض قبل ربط المتجر، دون السماح له بقراءة بيانات متجر قبل التفويض. اختُبر ذلك في وضع الإنتاج على PostgreSQL محلي.

الاختبارات الحية مع Shopify: **لم تُنفّذ**، لغياب الاعتماديات وHTTPS والتفويض. لا تعتبر أي استجابة mock أو نجاح بناء اتصالًا مثبتًا أو قبولًا نهائيًا.
